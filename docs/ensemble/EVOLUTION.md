# Ensemble 设计怎样一步步形成

这是一份供学习与反思的演进阅读。编号表示归纳后的推进顺序，不记录日期、时刻或工作耗时。初始条目依据本会话可见讨论、既有设计材料和共享任务回溯整理；并行调查可合为一步，不伪装成每次编辑的精确先后。这里由 Lead 在插件开发前编写，尚未经过计划中的自动档案与出版工具。

当前规范见[正式设计](README.md)，方法见[技能](../../skills/ensemble/SKILL.md)。历史研究保留为证据，不覆盖新的要求；源码阅读、提案、运行观察分别表述。本文从临时研究档案整理进入产品仓库，保存可复用的设计依据、失败与更正；具体环境配置和逐次运行记录仍由私有档案保存。各条描述当时的判断，后续更正明确标注，当前规范优先。

## 01 从方法价值出发，而不是复制旧工具

**起点。** 目标是让 ensemble 利用 DSH 原生代理与协作。直接照搬 OMP 的状态 writer 或固定提交动作，容易把适配器现状误当方法本身。

**判断怎样改变。** 方法研究把价值与手段分开：独立贡献、证据取舍、一个可验证候选和可恢复判断应保留；具体写文件工具、成员生命周期和提交仪式可以改变。协调者也不应因早期角色约束而被禁止研究或实现。

**教训与局限。** “这个规则由旧 harness 限制产生”也需要证据，不能把所有不喜欢的流程都推给技术限制。以后先问规则保护什么，再问新能力是否真正承担了它，而不是删掉旧名字就算完成适配。

关联：[早期方法研究](../../.ensemble/002-dsh-adaptation/METHODOLOGY-RESEARCH.md)、[正式方法](../../skills/ensemble/README.md)。

## 02 把异构、冗余与独立性分开

**起点。** 早期讨论容易把跨模型视为唯一有效差异，或把同模型组合统一叫作降级。用户明确指出不同提示、方向、工具、方法和思考强度也有价值。

**证据与修正。** 本次研究者实际使用同一模型，分别沿执行链和 Client 文件链发现不同问题，这支持任务方向差异的实用性，但不构成跨模型运行证据。方法因此分别判断：差异会改变什么、是否重复观察同一问题、首次结论前接触过什么。

**留下的教训。** 同模型可以揭露共同模型的错误，但重复或一致不能排除共同盲点。不同 provider 名也不证明不同底层模型。下次组合应从要减少的不确定性选差异，而非从角色或模型数量推断质量。

关联：[异构复核](../../.ensemble/002-dsh-adaptation/HETEROGENEITY-RESEARCH.md)、[词汇](../../skills/ensemble/GLOSSARY.md)。

## 03 不把运行会话与目标源码拼成一种版本

**起点。** 本次实际工具仍有旧具名 Team 的形态，而目标源码已采用统一 subagent 树。若据当前工具缺少参数设计长期补丁，会把旧限制带进新插件。

**工作与变化。** 建立独立可写源码副本并拉取官方上游。核验结果没有新增提交；真正变化是用户明确只支持新版。研究确认新版原生工具已提供逐成员 provider/model/effort 选择，旧 Team bridge 从实施范围撤出。

**教训。** 有源码能力不等于当前部署已经开放它。版本没有变化也可能需要重写设计，因为支持目标变化了。不能为了显示进展把零差异拉取包装成升级。

关联：[基线记录](../../.ensemble/002-dsh-adaptation/UPSTREAM-BASELINE.md)、[新版执行研究](../../.ensemble/002-dsh-adaptation/NEW-DSH-EXECUTION-RESEARCH.md)。

## 04 公共接口存在，还要追到实际消费者

**起点。** “技能能读文件”“已有 Markdown 渲染器”“Client 可以打包”都看似足以完成插件。

**实际发现。** skill resourceBase 只是提示，不会把 Host 安装目录映射到容器；公共 Markdown primitive 不保证严格链接允许范围；仓内 Client build preset 不是仓外发布依赖。模型选择也有省略语义：显式 route 但不写 effort，与全部省略不是一回事。

**方法改进。** 接口研究要继续问字段在哪里被消费、配置在什么时点生效、谁拥有文件坐标。技能参考资料、受限渲染、真实包安装和 actual request 验收因此成为具体工作，而不只是宣称复用。

关联：[Client 复核](../../.ensemble/002-dsh-adaptation/NEW-DSH-PLUGIN-RESEARCH.md)、[实施准备](IMPLEMENTATION.md)。

## 05 Lead 的直接工作权利，不应遮住编排和教学责任

**起点。** 纠正“协调者不能做事”之后，方案仍没有充分表达强 Lead 的主要价值。用户补充：它应重点编排一线模型，教导并优化其工作方法。

**变化。** 工作流增加早期可审产物、针对具体误差的教学、原例修复、未教过的邻近案例与非作者复核。教导改变指令与方法，不是训练权重；给过答案后的修订也不再计作独立首轮。

**教训。** Lead 亲自修好问题，可能交付了结果却没有改善成员能力；成员复述正确答案，也可能没有迁移。以后应分别记录交付改善和方法应用证据，并保留一条未继承争议结论的评价路径，反驳 Lead 自己的教案。

关联：[教学研究](research/LEAD-LEARNING.md)、[领域学习流程](DOMAIN-MODEL.md)。

## 06 环境与高频历史不应进入产品提交

**起点。** 原方法说把状态与代码分开提交，但它们仍污染同一主仓库历史。具体可用模型、provider 与日志也会频繁变化。

**修正。** 用户提出独立集约存储后，设计把产品方法、环境配置、操作历史和启发性阅读分开。项目档案各有身份与授权，环境偏好由本地部署拥有，凭证保留在原生 owner 中。单独的 Git commit 不是单独的存储责任。

**暴露的限制。** 本轮尝试在研究容器中建立工作区外位置，文件系统返回只读。这只证明当前容器没有那个可写位置，不证明正式 Host 插件不能做到。没有更换容器或扩权；临时研究留存与未来正式布局明确分报。

关联：[档案设计](ARCHIVE-DESIGN.md)、[DSH 接入研究](research/ARCHIVE-SEAMS.md)。

## 07 真正替代目录，需要表达覆盖而非几个新按钮

**起点。** 一度用“提交贡献、取舍、验证、教学反馈”概括新工具。用户指出这是替代 `.ensemble/`，必须覆盖整个目录的表达。

**改变了什么。** 逐项列出状态模板：目标、范围、覆盖、完成判据、尝试状态、取舍、候选、检查、缺失、风险、下一步和阻塞；再补目录中真正存在的长研究、设计、术语、未知章节与附件。Artifact 成为可独立保存、修订和读回的内容，不必先被压缩成 lesson 或 reflection。

**教训。** 更结构化的 Interface 可能悄悄减少表达能力。以后先建立旧能力到新命令的完整矩阵，再检验一条无手写文件的正常路径。导入读不懂的段落时保留原文；不能把丢内容称为“规范化成功”。

关联：[完整替代矩阵](REPLACEMENT-MAP.md)。

## 08 自动历史先解决提交点，而不是定时执行 Git

**起点。** 外置目录加自动 commit 看起来很直接，但文件写成功、Git 发布成功、模型收到结果和 UI 更新不是同一件事。原生 storage 的进程内串行也不是跨进程事务。

**研究改变的设计。** DSH 接入复核发现：storage-json 无跨进程写锁，domain 可持旧 snapshot；锁住更新不一定避免覆盖。设计改用 plugin-owned Git ref 作为记录和 Markdown 投影的唯一发布点，绑定也在同一事务；cache可重建。Host archive 的本地进程必须与 source execution world 分开。

**教训与待证。** 准备好 commit 对象不代表发布了 ref；发布后响应丢失应按操作收据对账，而不是盲目重试。Git 官方语义支持设计方向，但本轮没有跑崩溃/断电注入，不能把 CAS 夸为任意文件系统的耐久保证。

关联：[事务与恢复](ARCHIVE-DESIGN.md#5-git-是唯一提交点)、[接入限制](research/ARCHIVE-SEAMS.md)。

## 09 用非作者反例纠正自己的防错规则

**起点。** 为防旧验证错误套用新候选，草案把新版本一律视为所有旧判断失效；为了不写时间线，又一概禁止所有时长；为了稳定阅读，还混用了 committed 与 published。

**被复核推翻的部分。** 方法审阅指出：小范围修订可显式说明旧观察仍适用，不能迫使伪造“重新运行”；性能测量是实质证据，不应被叙事格式删去；未出版的贡献、artifact 和反思草稿必须能正常读改审。执行审阅另指出 approval never 不自动撤销已有 app-data 授权，管理操作和新 lesson 创建也需要明确入口。

**改进。** 同步修正领域状态、工具说明与验收向量，并把关闭后学习/反证、blocked恢复和reopen写清楚。有效复核不是多写几条禁止事项，而是找到“本规则会误杀哪个合法正常行为”。这些修改仍需要运行测试，不能把审阅通过当最终证明。

关联：[领域模型](DOMAIN-MODEL.md)、[工具与授权](ARCHIVE-DESIGN.md)、[实施向量](IMPLEMENTATION.md)。

## 10 从保存经验转向值得精读、可用于下一次工作的阅读

**起点。** 用户提供的另一项目日志展示了问题、行动、证据、修正和反思的关系，并要求这种产出本身成为工作流能力。其网络协议结论不属于本项目，方法经验却能迁移。

**形成的模型。** Checkpoint回答当前如何继续；history保留发生了哪些变更；evolution reading解释判断为什么改变；lesson描述在什么条件下采取什么动作。程序管理身份、顺序、来源、分域、审阅版本和发布，Lead负责有证据的解释，非作者可以否定因果与过度推广。内容较大时按问题域拆精读材料，概览只说明交接与影响。

**下一步怎样验证。** 先实现一次完整 open→贡献→判断→验证→反思→检索的切片，挑未教过的任务检验经验应用。若下一位成员只复述故事、无法指出适用条件和反例，这份阅读还没有达到目的。正常操作、成对失败例、真实 Loader/Host/Client 组合与实际模型请求分别取证，而不是继续用字数和链接数评价成熟度。

关联：[演进阅读功能](../../skills/ensemble/EVOLUTION-TEMPLATE.md)、[切片与验收](IMPLEMENTATION.md)。

## 11 路线图先评估设计是否闭合，再安排代码

**起点。** 用户要求从当前文档到全部承诺功能的路线图，并明确第一步是完善整个设计图景。既有设计虽然有 A–F 技术切片和验收向量，却仍缺初始化与管理、逐动作状态/权限、环境历史与实际配置应用、导出和长期维护的完整路径。

**证据怎样改变计划。** 两位 teammate 分别检查方法承诺和实际包/OMP 基线，发现现有可执行包仍只有 OMP；接入设计不是已经存在的 DSH 能力。路线图据此将当前阶段定为总体方案与关键约束已有、详细设计仍需闭合，新增 P0 出口，再安排组合探针、可靠事务、完整协调、学习出版、用户表面、数据维护与发布。环境历史保存和原生配置应用被拆成两个成功点；发布包还要证明私有档案不在包内，不能只检查必需资产齐全。

**用户提醒暴露的遗漏。** 两位研究者已受委托并行工作，但路线图仍把 teammate 藏在“原生执行”概括中，本轮共享任务登记也不完整。提醒后补齐任务登记，并把成员创建/绑定、任务领取、工具与档案授权、消息等待、教学复用、迟到替换、恢复与接管独立列为设计项和验收项。Team 可选，不能因验收任务板而让整个 ensemble 方法强制依赖它。

**保留的范围问题。** 旧文同时写首版不自动同步与远端同步留作后续。路线图不能替用户静默选掉后者，因此保留为 P0 必须明确处分的范围，而不是宣称已排除或已实现。未决业务规则不能整项推给技术探针；真正需运行才能回答的问题才可带着有界预期进入下一阶段。

**教训与下一检验。** 完整的路线图应揭露各阶段缺什么证据，不能只按模块排工期。接下来要让非作者演练新项目、旧资料迁移与下一任务经验应用三条路径，核对每一步都有可信输入、合法动作、保存点、读回结果和失败后动作。本轮仅完成规划与文档审查，P0 和所有功能阶段仍未验收。

关联：[路线图](../../ROADMAP.md)、[覆盖研究](research/ROADMAP-COVERAGE.md)、[交付依赖研究](research/ROADMAP-DELIVERY.md)。

## 12 把成员名称还原为能力与上下文选择

**更正条目 11。** 用户说明“你忘了 teammate”是在提醒 Lead 积极使用 subagent，并不是要求独立 teammate 领域层。此前我把提醒解释成路线图缺少特殊协作产品，随后又据当前运行时工具推断选型入口缺失，均超出了证据。现行设计统一使用原生代理；Member/Attempt 保持原有职责，协作验收保留，但不新增成员类别。

**证据与取舍。** 全新研究代理分别核对上下文驱动和固定源码；当前部署的独立探针仅说明其直系消息与工具限制。当时研究的开发快照（包版本标为`0.2.2-rc.3`，非正式发行tag）、提交`39163dd30f703a79079e2d2446545cff3c453738` 实现同树代理互通和可选共享任务板，fresh/fork 都能续做。源代码决定目标能力，当前部署不能替代目标验收。任务领取、消息受理、贡献采纳、档案授权也不能相互推导。

**模型选择的纠偏。** 普通工具的 schema 没有模型字段不代表所有入口都没有；本会话 workflow 已提供 provider/model 覆盖。目标源码更已有 spawn 的原生选型开关、路由授权与预检，优先配置现有实例即可，不需要先造包装。作用域覆盖虽可行，同层重复注册仍拒绝，单改 schema 也不改变执行器授权。包装若把模型参数伪装成受信 defaults，会丢失原生策略语义。

**能力不等于适用决定。** 我一度把 fork backend 支持换模推成应默认开启。用户指出思考及部分上下文跨模型可能不兼容；最终决定是 fresh 选择 provider/model/effort，fork 保持原路由。若考虑 fork 同路由 effort 调整，先定义原等级、目标等级、升降方向和受限执行器；不以“提高思考”替代具体能力核验。跨模型异构主要靠新代理与可审任务包；已有成员用于续做教学，独立性仍看答案暴露，而非名字新旧。

**下一检验。** 在目标版本真实组合中验证 fresh 选型、fork 固定路由、同级消息及 Team 开关/领取；对可选 effort 方案用未知基线和路由变化反例。设计文档与路线图已明确版本和这些门槛，本轮不把源码阅读或链接检查计作运行验收。

**执行反馈。** 指定 Flash 路由的广范围调查未返回报告，取消后收窄到四段关键源码才完成；首个 provider 拼写请求返回 null，也未计作成功。定向复核仍混淆了插件默认与标准组合默认，并对 effort 和作用域作了过强概括，Lead 根据完整调用链收紧。快速模型的工作包仍需有界、可审，最终结论不能只照抄返回值；本次没有足够对照来声称速度或质量提升。

关联：[原生代理接入决定](NATIVE-AGENTS.md)、[驱动研究](research/AGENT-DRIVING-CHOICES.md)、[源码能力研究](research/NATIVE-AGENT-CAPABILITIES.md)、[Flash 核验与处分](research/MODEL-SELECTION-FLASH.md)。部署探针仅能说明当次会话，原始运行记录未纳入产品仓库。

## 13 续用的价值取决于任务与上下文是否匹配

**问题与更正。** 用户指出：保留上下文的成员领取新任务，不代表旧上下文与任务有关。现有驱动矩阵虽允许fresh，却没有把分派/领取前的匹配判断写清。“续用不增加独立样本”也过宽，应该限定为同一判断的继续或修订；无关旧历史不自动破坏新问题首轮的独立性。

**设计变化。** 将相关性、时效性、答案暴露、上下文负担和重建成本放在分派判断中。Lead 可以专门创建fresh成员，不必等到已有成员全部不合适；也可让熟悉背景的成员继续工作，另开fresh审查者。fresh只是新对话，同一树内的授权共享任务仍可读回。领取确立owner，不代表必要上下文已加载；新旧成员都读取当前任务与证据，换人按原生所有权交接。

**反例与验证。** 全新审阅代理提出两个有效反例：做过界面文案的空闲成员不因“已有上下文”就更适合并发审计；fresh成员若读到“根因已定，请证明”的任务描述，也不能算独立根因判断。已把匹配、fresh加入共享任务及答案暴露场景加入路线图验收；本轮仅改文档，未运行目标DSH协作流程。无需增加匹配评分器、永久角色表或新的记录格式。

## 14 用发布标签定位接入版本，而不只读取开发分支包版本

**证据改变。** 用户提醒npm next已发布0.2.2-rc.4。registry与正式tag核验后，现行基线改为`3f321d32bfe382212a8ed8785c1d47a5a300aa23`。条目12的`39163dd…`仍准确指向当时研究源码，但它是包版本标为rc.3的master快照，不是rc.3发行标签；两个端点非线性。正式rc.3→rc.4的净变化远小于开发快照→发行版本的差异，必须分别报告，不能把所有移除都说成rc.4回退。

**设计处分。** 原生代理树、任务共享、fresh选型及fork保持路由的决定可保留。发行接口缺少开发快照中的部分细分错误码和workflow.errorCode，skill出口及Cordis根上下文写法也不同；实施应对发行包类型编译，不能照搬master。真正的发布行为变化是DeepSeek拒答明确为CONTENT_REFUSED及Desktop liveshare worker启动修复；拒答不形成成功贡献。

**复核与保留。** 两路Flash定向复核后，Lead检查关键净diff与源码，收紧了“所有错误码消失”“注释变化导致更早失败”等过强说法。旧研究checkout和SHA引用保留，新发行单独worktree；链接校验按各自SHA解析，现行设计只引用rc.4。已更新实施约束和验收向量，但没有运行安装、构建或GUI升级；npm缺失不妨碍从registry验证发布事实。

## 15 用实际调用反例补齐文档交接

**问题。** 总体设计已有外置档案、原生执行和学习出版的分工，但文档仍让实施者决定字段、状态和恢复细节。当前OMP说明又把只有托管档案才有的open动作写成通用入口；角色加载完整技能后，成员职责也需单独界定。

**证据与修改。** 两路独立审查分别读领域设计和实际OMP源码，Lead补出命令约定、运行管理及三条用户旅程，更新逐项表达样例和路线图责任。始终Git版本化解决了“可关闭历史”与唯一提交点的矛盾；环境保存和实际应用分别对账；远端明确为单主复制与隔离恢复。

**调用反例揭露的漏洞。** 新required覆盖项和判据分开提交会互相卡住，改为requirements原子组；完成请求只列旧pass会掩盖新fail，改为检查全部适用观察并要求解除链；旧备份缺失较新收据却沿用身份，会破坏幂等，恢复因此要求最后权威head证明或明确的新身份。旅程审阅还发现proposed经验不会出现在默认supported检索中，试用入口据此显式选择未评估版本。

**可复用的方法。** 一项约定应能用具体调用说明谁输入、引用哪版、何处保存、谁消费、失败如何继续。单纯多写原则不能暴露“两个合法动作无法依次完成”或“旧状态被另一动作复活”的漏洞。将这些反例纳入R21–R30，让后续实现沿同一语义验证。

关联：[审阅与处分](research/DOC-CLOSURE-RESULT.md)、[命令约定](COMMANDS.md)、[运行管理](OPERATIONS.md)、[用户旅程](USER-JOURNEYS.md)。

## 16 共享方法源，分别交付使用上下文

**新增需求。** 用户要求纯skill、OMP与DSH在安装和使用时分别闭合，尤其DSH不加载其它路径说明。原方案把可移植性落实为同一正文中的多种条件分支，又准备给同一发布包增加DSH入口；这些做法与新要求冲突。

**证据与取舍。** 两路独立调查分别核对分发约束和比较维护成本。Lead直接读取OMP provider，确认它从扩展根的skills目录发现技能；当前正文、模板、参考和README也确有跨路径内容。因此拆三个入口标题不足以隔离，需覆盖整个安装/加载/参考闭包。

**当时设计（纯skill发行仓选择已由条目17更正）。** 保留一份不含平台操作的common源，用一个确定性脚本与三份显式清单，产出完整普通Markdown及路径内参考。OMP和DSH分别从干净根打包；纯skill使用自动生成的干净Git发行仓。与研究者建议保留纯skill母仓地址相比，发行仓还把安装来源本身和多路径维护说明分开，代价是增加一个自动发布目标，不增加人工维护的方法副本。OMP可沿用原包身份和其它技能，DSH使用独立身份；旧混合Git安装入口随发行迁移。

**反例与下一检验。** DSH入口干净而reference回读旧混合模板、OMP包自动发现另一个同名技能、npm白名单通过而包README或Git来源仍混用，都应使验收失败。P1建立三个实际产物，R18逐路径检验安装、角色autoload、全部参考和本地链接。

关联：[当前分发设计](DISTRIBUTION.md)、[OMP核验与处分](research/PATH-ISOLATION-OMP.md)、[独立方案比较](research/PATH-ISOLATION-DESIGN.md)。

## 17 保留纯skill原有Git安装地址

**更正条目16的发行选择。** 用户询问`npx skills@latest add vcup/skills`能否继续安装纯skill，随后要求更新文档。另建纯skill发行仓会改变这个入口，且并非隔离安装内容所必需，因此改为保留原Git来源。

**当前方案。** 在同仓维护common与三路径说明，将完整纯skill生成到`skills/ensemble/`并随Git提交；入口源不命名为SKILL.md，OMP/DSH同名产物只进入各自发布包。纯skill的参考全部留在其目录内，安装不依赖构建或母仓库文件。OMP仍需从旧混合Git入口迁移到独立包，纯skill命令保持不变。

**下一检验。** 分别验证不指定技能和显式`--skill ensemble`的真实发现/安装结果，记录安装器解析版本；CI重生成须与已提交内容一致，检查安装目录及所有参考不带入其它路径。源仓共同维护不等于安装结果混用；关键是技能发现与内容复制后的实际范围。

## 18 让长期设计证据进入正式仓库

**问题与更正。** 把环境配置和高频运行记录放进私有档案是必要的，但此前也将源码研究、独立审阅、设计演进和检查脚本留在临时目录，导致重要依据不能随项目共享。用户要求整理并提交这些资料。

**处理。** 长期研究与审阅归入[研究索引](research/README.md)，本文保存判断变化；既有早期资料引用仓库中的原版。运行环境探针、第三方源码副本与临时缓存继续保留在本地。文档检查脚本改为从自身位置定位仓库，默认不依赖私有档案或本机上游checkout。产品资料与用户运行档案因此分别获得合适的保存位置。
