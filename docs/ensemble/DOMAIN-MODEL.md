# 协调与学习领域模型

本文件定义面向 DSH `0.2.2-rc.4` 的 ensemble 插件的业务事实与可观察行为（固定源码基线见[设计入口](README.md)）；存储实现见[档案设计](ARCHIVE-DESIGN.md)，具体实施入口见[实施计划](IMPLEMENTATION.md)。术语以[方法词汇](../../skills/ensemble/GLOSSARY.md)为准。领域划分源于不同的事实和变化原因，不要求每个模型各占一个 npm 包。

## 1. 身份与权威

| 对象 | 身份与内容 | 权威/寿命 |
|---|---|---|
| Project binding | 受用户控制的 source workspace 身份与私有 archive 的关联 | 配置/绑定 owner；不是 remote URL 或 cwd 字符串相等 |
| Invocation | 一次完整交付目标、约束、覆盖与当前候选 | 协调模型；可跨原生会话恢复，显式接管后更换 Lead |
| Attempt | 问题、基线、预期贡献、差异/冗余理由、首轮已暴露信息 | 协调模型；不等于一次 tool call 或成员身份 |
| Contribution | 作者、所属 attempt、摘要、产物/观察引用与版本 | 作者提交，Lead 处分；旧版本保留 |
| Archived artifact | 研究正文、原始摘录、设计、未知内容或证据附件，含类型、字节/digest与修订关系 | 可独立于 contribution/reflection 保存；程序拥有路径/版本，模型可提交正文 |
| Candidate | 本次交付的具体 source revision、patch digest 或 artifact revision | 协调模型引用，外部产物仍由项目拥有 |
| Finding | 独立的问题、机会、缺口、风险或未决选择及其影响与证据 | 任何获准参与者可提出；Lead对确切版本作决定 |
| Check | 所检验candidate、finding、lesson或publication版本、前提、实际操作、结果、证据与局限 | 提交者声明；若由可信采集器观察须显式区分 |
| Challenge | 针对既有判断版本的反证与影响 | 提交者提出，Lead处分；保留被挑战判断及其旧适用范围 |
| Coaching intervention | 哪个具体误差、采取什么指导、暴露了什么、预期改善及验证 | 学习模型；不修改 model weights，不替执行模型选路 |
| Reflection | 从工作事实提出的因果解释、变化、限制、未来检验 | 具名作者提议；审阅/发布是独立判断 |
| Lesson | 情境→建议动作、依据、反例、适用/失效条件 | 学习模型；不是从已发布文章自动变成规则 |
| Reading collection | 面向特定问题/读者的稳定领域与文章顺序、概览 | 出版模型；可分拆但条目身份和交叉引用稳定 |

这些身份由程序生成、校验并传回。模型提交语义内容和已知引用，不负责路径、序号或文件格式。作者、调用 Session、原生 agent 身份从执行上下文派生，不能接受模型伪造的 `author`、`reviewer` 或 `isVerified`。

Member 统一指参与 ensemble 的原生代理，不另设 teammate 类型。fresh、fork、续用是上下文与驱动选择，理由及已暴露信息归入 attempt；通信、原生共享任务和档案权限分别核验，不能由驱动名称推导。原生 agent catalog name 用于实际通信；档案引用保存其稳定 Session 身份与当时名称，不用当前同名成员覆盖历史。原生 execution/task 状态可在 UI 旁边展示为有观察时点的独立信息，不复制为协调状态机，也不从 `inactive` 推导成功。

## 2. 一次交付的正常行为

输入例：用户要设计一个插件，需要执行选择、外置档案、学习出版和 UI，不能把“可打开一份 Markdown”当全部完成。

1. **Open** 接收目标、必要覆盖和完成标准，在已授权项目中创建 invocation。`active` 只代表工作进行；程序生成当前检查点，返回身份/revision。
2. **Plan attempt** 由 Lead 指定问题、共同基线、预期产物、差异或冗余、写入范围与首轮信息来源。native agent 可以尚未创建；后续绑定真实返回身份，不伪造“已经派出”。原生创建失败，计划保留为未执行，不以回滚 Git 隐藏失败。
3. **Put artifact / Submit contribution** 成员可先保存完整研究正文、原始资料或其它 artifact，无须先产生反思/经验；程序分配身份并返回可引用版本。成员再提交或修订贡献，引用该产物，状态 `submitted`；程序不自动接受。没有绑定成员时只能由 Lead 登记外部贡献并注明来源，不伪装该成员亲自调用。
4. **Decide** 由 Lead 对特定贡献版本作出 accepted / rejected / revise / deferred / unresolved，附理由与证据。Deferred 包含未完成覆盖，不能靠归档改名变成已完成。后续版本使旧决定的当前适用性待核；Lead 可重新采纳或显式说明未受影响的判断，不强制把小改动扩成全量重审。
5. **Set candidate / Record check** 指定一个整合对象，检查保存自己真正观察的版本。新 candidate 不自动继承旧通过状态；允许 Lead 通过 applicability record 引用旧检查、影响分析与仍有效范围，把适用部分关联新候选，不能称为重新执行。相同环境、相同树也不被系统自动猜为等价。
6. **Close** 明确交付结果、各必要覆盖所关联贡献/决定/检查，以及未完成项。必要项未处分、关键检查失败或缺失时拒绝 `completed`；用户明确改变范围须先作为可追溯 scope amendment，不能由模型偷偷 waiver。允许 `blocked`/`abandoned`，但不显示为成功。

Close不是所有写入的终态：blocked可恢复，completed后仍可追加反思、artifact、反证及更正，Lead可据challenge显式reopen；出版状态独立于交付状态。各转换、允许动作和完成谓词以[命令约定](COMMANDS.md#4-状态与完成条件)为准；[替代矩阵](REPLACEMENT-MAP.md#3-关闭恢复与学习不共用一个状态机)给出表达与读回示例。

代码可验证“必要项都被有权限的人处分”“检查引用当前 candidate”“未把失败标通过”，不能从自然语言证明需求已真正满足。最终完成是 Lead 的可审验收声明， UI 保留其来源与证据模态。

## 3. Lead 如何教，而不消除独立性

正常教学路径：成员先给出一个具体产物；Lead 指出可复现问题，区分输入不足、方法错误、工具不可用和模型能力限制；给可执行指导；成员修复；用未教过的相邻案例及反例验证迁移。改 prompt、增加工具、调整 effort、换模型是不同干预，不能混记成“升级有效”。

| 阶段 | 可以提供什么 | 对独立性的影响 |
|---|---|---|
| 独立首轮之前 | 需求、原始证据、公开规范、一般方法和成功标准 | 仍须检查材料是否暗含比较对象答案 |
| 提交首轮之后 | 精确反例、Lead/sibling 论证、示范修复 | 产生 guided revision，不新增独立首轮样本 |
| 验证教学 | 未在教案中暴露的新案例；一条非作者评估路径 | 能支持局部迁移，不证明所有任务上的能力提升 |
| 高风险必要信息出现 | 及时通知可能受影响者，不为盲评隐瞒 | 记录暴露，必要时另开独立评估路径 |

首轮“结论锁定”不是秘密沙箱：普通共享文件/任务板仍可能泄露。工具记录已知暴露关系，并拒绝把 guided revision 自动计为 independent；不能证明成员没读过未观察到的材料。

教学验证记录原例修复、邻近未见案例、反例与审查结果；缺少任一相关依据则相应主张保持 proposed/untested。不能把单次变化归因于某个模型或教学策略而忽略候选、任务难度、工具和其他干预同时变化。没有可比对照时只写“这次应用有效”，不报告因果提升率。

## 4. 环境选择与经验的交接

Lead 的“更强”由任务适任性及本地经验支撑，不在通用方法里写死排序。环境 owner 可配置角色偏好：候选 provider/model、该 route 支持的 effort 与允许 preset。推荐结果必须附当次可用性/授权诊断，执行仍通过原生子代理工具；不存在可用 route 时返回缺口，不静默换成别的模型。

三个配置证据分别保留：请求选择、创建描述、实际模型请求。前两者不能证明第三者；不复制完整 request prompt 或 credentials。全省略、显式 route 省略 effort、显式 effort 的 native 语义不同，详见[实施原生选择](IMPLEMENTATION.md)。

推荐/经验读取不自动修改角色偏好、Session 授权、root 模型或成员模型。变更部署偏好属于用户可审配置；它发生变化不让历史经验消失，只使其适用性重新检查。模型别名和 provider 名不同也不自动证明不同模型先验。

## 5. 四种记录，各有用途

| 内容 | 读者要回答的问题 | 更新方式 |
|---|---|---|
| Checkpoint | 当前目标、判断、候选、缺口和下一步是什么？ | 程序从已接受领域命令投影，替换当前视图 |
| History | 哪些事实/声明被谁以何次操作改变？ | 版本化的结构化命令结果与 Git，不能据顺序推导因果 |
| Evolution reading | 哪个发现改变了判断，为什么，后来者该如何反思？ | 带引用的反思提案、审阅、出版与更正 |
| Lesson | 遇到类似情况该做什么，何时不适用？ | 有范围的提炼与应用反馈，证据不足不强荐 |

模型不用维护这四份文件。一次领域动作的事实先落盘；程序可标出“已有未解释的重要取舍”供 Lead 阅读，但不自行调用隐藏模型或从每次工具返回生成故事。Lead 在用户已启动的工作流中提交反思内容；确定性代码负责校验、出版与版本。

## 6. 反思、出版与修订

Reflection 包含：主领域、标题、起点问题、行动与证据、判断变化、反思与限制、下一检验、关联事实版本；可标为回溯整理及来源不全。它是结构化章节内容，工具不接受任意整篇 Markdown 替换。章节内允许普通叙述；不通过复杂写作 DSL 限制观点。

正常流程是 `draft → reviewed → published`。作者可修订 draft，审阅绑定 exact draft revision；修订后旧 review 失效。非作者 review 报告证据是否支撑主张、遗漏的反例、混淆的完成状态；有阻断问题时不能发布。Lead 授权发布，但不能替别人伪造 review。只有作者一人可用时保留可读 draft 与未审状态，不伪称独立复核；交付代码并不必须等每篇 draft 出版。

程序按发布顺序分配编号，不按作者猜测的真实发生时间排序；叙事标题与推进描述不写日期、时刻或工作耗时。证据本身的测量值、有效性条件不能为了这种写作格式删除，可保留为明确标注的观察或原始材料引用。Git 与原生 operational log 的时间元数据保持原样，不能为满足叙事格式伪造历史。并行工作可在一个有证据的条目中归纳，明确这不是逐次编辑的精确先后。

已发布内容纠错：新增 amendment 解释原主张、纠正依据、影响范围与 supersedes 关系。原文与旧 revision 可读，当前视图显著标注更正。错链/拼写也经过 revision，不从底层改旧 Git objects。撤回误导性条目或 lesson 与删除历史不同；敏感材料清除另走用户维护流程，不能承诺 append-only 同时消除所有副本。

## 7. 分域精读与经验检索

先有一个小概览；当问题域/读者明显不同或篇幅妨碍精读时，Lead 提议 collection split。领域定义包含问题范围与面向读者，不按成员数量自动拆文件。迁移已有条目只改归属映射，不改条目身份或伪造新的发生顺序。

跨域事件只有一个主叙事；其他领域写必要后果并引用 stable entry id/revision。概览链接主题及相互影响，不复制每篇正文。一个领域的“完成”不能使另一领域的失败条件自动消失。

Lesson 从已审主张中单独提议，字段为 trigger、recommended action、supporting evidence、counterexample/non-applicability、invalidation condition、applicability（任务种类/接口版本/必要能力）。状态 `proposed / supported / contested / retired`；supported 必须有相关应用观察，published reflection 不是支持的充分条件。出现反例，保留 supporting 与 contradicting evidence，撤去默认推荐或标 contested，再评审适用范围。

首版检索是领域/任务/适用性过滤加可解释文本搜索，先返回标题、短适用条件、状态和必要证据链接，再按需取正文。没有足够上下文时标未知，不能自动按发布日期或被引用次数宣称质量。Token 上限由完整响应预算控制；超限提供分页/缩小问题，不静默删掉限制段。无跨项目自动训练、向量数据库、全量背景注入或全局自动 prompt 改写。

## 8. 什么使这套工作流更有用

检查演进阅读是否能让非作者回答：原假设是什么、哪条独立证据改变了它、做了什么取舍、哪些情况仍不成立。检查经验是否让下一位成员在新例上改善，而非复述旧文。检查看板能否区分 submitted、accepted、verified、published，且始终指向正确版本。

完整历史、无断链和流畅叙述只是基础。未经运行的验收向量仍是提案；研究报告可以详尽但实现仍未可行。各自的反例与实施门槛见[验收矩阵](IMPLEMENTATION.md)，不把文档成熟度等同于运行资格。
